## 1. 业务对象分析

### 1.1 从业务流程提取对象

**V1 业务流程：**
- 用户打开 App → 看到 Today 首页（日期 + 纪念日卡片 + 日记入口）
- 用户写日记 → 输入文字 + 选心情 → 保存
- 用户查看历史 → 日历视图 → 点击某天看日记 → 编辑/删除
- 用户添加纪念日 → 输入标题 + 选日期 + 选 emoji → 卡片展示已过天数

**提取的业务对象：**

| 对象 | 来源 | 生命周期 |
|------|------|---------|
| **Diary（日记）** | 写日记操作 | 创建 → 编辑 → 删除 |
| **DayCounter（纪念日）** | 添加纪念日操作 | 创建 → 删除 |

### 1.2 确认对象关系

```
Diary ──── (独立) ──── DayCounter
   │                        │
   └── 通过 date 字段 ──────┘
       （逻辑关联，非数据库外键）
```

- V1 两张表**完全独立**，没有任何数据库级外键
- 它们的关联仅在业务层通过 `date` 字段的等值匹配实现
- 这种设计保留了将来任意拆分的灵活性

## 2. 数据库选型

### 2.1 主数据库：SQLite（唯一选择）

**选型理由：**

| 维度 | 决策 | 原因 |
|------|------|------|
| 数据规模 | ✅ 适合 | 个人单用户数据，日积月累最多数万条，SQLite 轻松支撑 |
| 部署方式 | ✅ 零配置 | 文件数据库，随 App 启动自动创建，无需单独安装 |
| 网络依赖 | ✅ 离线 | 纯本地，不依赖任何远程服务，符合「本地优先」原则 |
| 性能 | ✅ 足够 | 单用户 CRUD，毫秒级响应 |
| 平台支持 | ✅ 原生 | Flutter sqflite 插件对 Android/iOS 均完美支持 |
| 迁移成本 | ✅ 极低 | 文件即数据库，导出备份就是复制一个 .db 文件 |

**不选的方案：**

| 数据库 | 为什么不选 |
|--------|-----------|
| **PostgreSQL / MySQL** | 需要额外服务进程，手机上无法运行 |
| **MongoDB** | 文档数据库不适合结构化日记数据，手机端无原生方案 |
| **Hive** | KV 存储，不支持 SQL 查询，后续做统计（月度日记数、心情趋势）时无法用 GROUP BY |
| **Isar** | 较新，社区成熟度不如 sqflite，国内学习资料少 |

### 2.2 Redis：不需要

| 问题 | 答案 |
|------|------|
| 是否需要缓存？ | 不需要。SQLite 本身就在内存中操作（打开后 cached），单用户不存在缓存命中率问题 |
| 是否需要 Pub/Sub？ | 不需要。单机单用户，无分布式事件分发需求 |
| 是否需要分布式锁？ | 不需要。单实例 App，| SQLite 文件锁已够用 |
| 将来 V5 加云端同步时需要？ | 届时再评估。本地 → 云端同步场景，Redis 不是核心依赖 |

**结论：V1-V5 均不需要 Redis。** 如果将来做多端同步，需要的是同步协议层（如 Supabase Realtime / WebSocket），不是缓存层。

### 2.3 本地开发与部署

| 环境 | 数据库位置 | 说明 |
|------|-----------|------|
| 开发（Web Chrome） | `path_provider` 获取的临时目录 | 每次 `flutter run` 可能重置 |
| 开发（Android 模拟器） | 模拟器内部存储 | 重启后保留 |
| 真机部署 | `/data/data/com.tracelife.trace_life/databases/` | 跟随 App 生命周期 |
| 未来 iOS | `NSDocumentDirectory` | 系统管理 |

**开发阶段测试策略：**
- Web 模式下每次刷新数据不持久（已知限制，可接受）
- 真机测试时数据持久保留
- 将来加「导出 JSON」功能实现手动备份

## 3. 表结构设计

### 3.1 日记表：diaries

| 字段 | 类型 | 约束 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键 |
| `date` | TEXT | NOT NULL, UNIQUE | — | 日期，格式 `yyyy-MM-dd` |
| `content` | TEXT | NOT NULL | `''` | 日记正文 |
| `mood` | INTEGER | NOT NULL, CHECK(1-5) | 3 | 心情指数 1-5 |
| `created_at` | TEXT | NOT NULL | — | 创建时间 ISO8601 |
| `updated_at` | TEXT | NOT NULL | — | 最后修改 ISO8601 |

**DDL：**

```sql
CREATE TABLE diaries (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  date       TEXT    NOT NULL UNIQUE,
  content    TEXT    NOT NULL DEFAULT '',
  mood       INTEGER NOT NULL DEFAULT 3 CHECK(mood >= 1 AND mood <= 5),
  created_at TEXT    NOT NULL,
  updated_at TEXT    NOT NULL
);

CREATE INDEX idx_diaries_date ON diaries(date);
```

### 3.2 纪念日表：day_counters

| 字段 | 类型 | 约束 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 主键 |
| `title` | TEXT | NOT NULL | — | 事件标题，如"认识你" |
| `target_date` | TEXT | NOT NULL | — | 目标日期 `yyyy-MM-dd` |
| `emoji` | TEXT | NOT NULL | `'📅'` | 表情符号 |
| `color_index` | INTEGER | NOT NULL | 0 | 卡片颜色索引（扩展用） |
| `sort_order` | INTEGER | NOT NULL | 0 | 排序权重（扩展用） |
| `created_at` | TEXT | NOT NULL | — | 创建时间 ISO8601 |

**DDL：**

```sql
CREATE TABLE day_counters (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  title       TEXT    NOT NULL,
  target_date TEXT    NOT NULL,
  emoji       TEXT    NOT NULL DEFAULT '📅',
  color_index INTEGER NOT NULL DEFAULT 0,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT    NOT NULL
);

CREATE INDEX idx_day_counters_date ON day_counters(target_date);
```

### 3.3 范式检查

#### 第一范式（1NF）：单一字段存单一含义 ✅

| 检查项 | 结果 |
|--------|------|
| date 字段只存日期 | ✅ `yyyy-MM-dd`，不含时间 |
| content 字段只存正文 | ✅ 不在 content 里拼"日期+心情+正文" |
| emoji 字段只存 emoji | ✅ 不是"🎉认识你"这种拼接 |
| 无逗号分隔字段 | ✅ 没有 `tags TEXT` 存"tag1,tag2,tag3" |

**被拒绝的设计（如出现必须说明原因）：**
- ❌ `content TEXT` 里塞入 `#心情:开心 #日期:2026-07-11` 之类的标记 → 违反 1NF
- ❌ `target_date TEXT` 存 `2026-07-11 00:00:00` → 混合日期+时间，违反单字段单一含义

#### 第二范式（2NF）：非主属性完全依赖于主键 ✅

- `diaries` 表：`content, mood, created_at, updated_at` 都完全依赖于 `id` 和 `date`（候选键）
- `day_counters` 表：所有字段完全依赖于 `id`
- 没有「部分依赖」问题（因为没有复合主键）

#### 第三范式（3NF）：字段之间不相互依赖 ✅

| 检查 | 结果 |
|------|------|
| `updated_at` 依赖 `id`，不依赖 `content` | ✅ |
| `mood` 不依赖 `content`，直接依赖 `id` | ✅ |
| `days_passed` 不存数据库 | ✅ 运行时从 `target_date` 计算 |

**被拒绝的设计：**
- ❌ 在表中存储 `days_passed INTEGER` → 违反 3NF（派生字段，可从 `target_date` 计算）
- ❌ 在表中存储 `is_future INTEGER` → 违反 3NF（同上）

### 3.4 反范式设计

V1 没有反范式设计。**所有表严格遵守 3NF。**

如果将来出现反范式（如为性能在日记表里冗余作者名），必须在此文档中说明：
- 字段名、冗余内容
- 性能瓶颈证据
- 同步策略（如何保证冗余数据一致性）

## 4. 字段规范

### 4.1 通用字段规范

| 规范 | 规则 | 示例 |
|------|------|------|
| **主键** | `INTEGER PRIMARY KEY AUTOINCREMENT` | 所有表统一 |
| **日期字段** | `TEXT`, 格式 `yyyy-MM-dd` | `'2026-07-11'` |
| **时间戳** | `TEXT`, 格式 ISO8601 | `'2026-07-11T14:35:00'` |
| **布尔值** | `INTEGER`, 0/1（SQLite 无 BOOLEAN） | `is_active` 字段用 1/0 |
| **字符串** | `TEXT`，有默认值用 `NOT NULL DEFAULT ''` | 避免 NULL 判断 |
| **索引** | 高频查询字段建普通索引 | `date`, `target_date` |
| **唯一约束** | 业务唯一键用 UNIQUE | `diaries.date` |

### 4.2 软删除规范

| V1 策略 | 理由 |
|----------|------|
| **不使用软删除** | 这是个人 App，用户主动删除 = 真的想删，不存在"恢复"需求 |
| 物理删除 | `DELETE FROM diaries WHERE id = ?` |
| 将来 V5 考虑 | 需要「回收站」功能时加 `deleted_at TEXT DEFAULT NULL` |

**如果将来启用软删除：**

```sql
-- 加字段
ALTER TABLE diaries ADD COLUMN deleted_at TEXT;

-- 所有查询加 WHERE deleted_at IS NULL
SELECT * FROM diaries WHERE deleted_at IS NULL ORDER BY date DESC;
```

### 4.3 金额计算规范

V1 无金额功能。V3（资产记录）启用时规范：

| 规范 | 规则 |
|------|------|
| 类型 | `INTEGER`，单位：分（cent） |
| 显示 | 前端除以 100 显示为元 |
| 不允许 | `REAL`/`DOUBLE`（浮点精度问题） |

### 4.4 密码存储规范

V1 无用户系统。如果将来加本地密码锁：

| 规范 | 规则 |
|------|------|
| 算法 | bcrypt（via dart `bcrypt` 包） |
| 存储 | hash + salt 一起存 |
| 不允许 | 明文 / MD5 / SHA1 |

## 5. 完整性检查清单

- [ ] 主键全部自增
- [ ] 日期字段格式统一 `yyyy-MM-dd`
- [ ] 时间戳格式统一 ISO8601
- [ ] 无逗号分隔字段（1NF）
- [ ] 无派生字段（3NF）
- [ ] 无冗余字段
- [ ] 外键关联（V1 无）有对应索引
- [ ] 字符串字段有 DEFAULT，避免 NULL
- [ ] CHECK 约束用于值域限制
- [ ] UNIQUE 约束用于业务唯一键

## 6. 建表脚本

```sql
-- TraceLife V1 建表脚本

-- 日记表
CREATE TABLE IF NOT EXISTS diaries (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  date       TEXT    NOT NULL UNIQUE,
  content    TEXT    NOT NULL DEFAULT '',
  mood       INTEGER NOT NULL DEFAULT 3 CHECK(mood >= 1 AND mood <= 5),
  created_at TEXT    NOT NULL,
  updated_at TEXT    NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_diaries_date ON diaries(date);

-- 纪念日表
CREATE TABLE IF NOT EXISTS day_counters (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  title       TEXT    NOT NULL,
  target_date TEXT    NOT NULL,
  emoji       TEXT    NOT NULL DEFAULT '📅',
  color_index INTEGER NOT NULL DEFAULT 0,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT    NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_day_counters_date ON day_counters(target_date);
```
